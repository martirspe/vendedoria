# Conversion and recovery engines

## Activation

1. Deploy the additive `20261005010000_conversion_engines` migration with the normal migrate service. Do not use `db push`.
2. Start the Redis service (private network, no public port, AOF, `noeviction`) and set `REDIS_URL`. Persist its volume. Redis is the BullMQ backend and ranking cache; PostgreSQL is the durable reminder outbox. Recovery is off for every tenant initially.
3. Configure the existing email provider (`EMAIL_MODE=live`, SES or Resend), plus `RECOVERY_EMAIL_FROM`: a verified sender for consented cart recovery, separate from the receipt address. Its identity must be allowed by the existing least-privilege SES policy. Keep suppression for bounce/complaint enabled; use the AWS audit before live sending. No AWS configuration is changed automatically.
4. For WhatsApp, connect the tenant's channel and obtain an approved **marketing** template in the configured language, with exactly three body parameters: store name, full recovery link and full opt-out link. The engine always uses a template, including after 24 hours; it does not claim that checkout creates a WhatsApp service window. Meta enforces approval. `EMAIL_MODE=preview` prepares both channel deliveries without contacting providers.
5. In **Tienda web → Recordatorios de compras pendientes**, an owner/admin enables the desired channels and saves increasing delays in minutes (default 15, 120, 1440; 1–3 intervals, max 4320 minutes). Swagger also exposes `GET/PUT /api/v1/conversion/settings` and `GET /api/v1/conversion/summary`. Turning recovery or a channel off is checked again by each worker before sending.
6. Optionally start Qdrant with `docker compose --profile recommendations-vector up -d qdrant` (add `-f docker-compose.dev.yml` for development), set `QDRANT_URL=http://qdrant:6333`, and recreate the API. In external deployments use HTTPS and `QDRANT_API_KEY`; keep the service private. It contains catalog features only, with a tenant payload index and mandatory tenant filter. It can be rebuilt from PostgreSQL; no buyer data goes there.

## Buyer behavior and privacy

- Classic, Selecta and Stride share recommendation and recovery components. Checkout presents a voluntary save action; exit-intent or 90 seconds of inactivity expands it once. It never submits contact data automatically or prechecks consent.
- Email and WhatsApp consent are separate, recorded with timestamp and version. The recovery capture form has its own Turnstile action (`recovery`) and per-IP rate limit. Capability actions retain their rate limit and do not require CAPTCHA.
- Only product handles, variants and quantities are saved; prices, visibility and stock are hydrated from the current tenant's catalog. Recovery may drop unavailable items and reduce quantities. The buyer reviews current prices before paying; saved carts never reserve stock. Card data, addresses and Yape codes are never part of recovery.
- Active interaction in cart/checkout sends a capability-authorized heartbeat at most once a minute while visible/recently active, keeping the selection current and postponing reminders. Closing the page needs no unload request. A checkout reservation links/stops the cart inside the order transaction; the worker also suppresses sends when a checkout for the contact exists since the capture.
- Recovery links are HMAC-signed, tenant-bound, expire after 7 days and contain no contact data. The URL is removed from browser history on use; recovery pages use no-referrer/no-store and skip analytics while a capability is present. Treat access logs as sensitive: redact `recover`, `stop` and order capability parameters at the edge.
- Revoking reminders or reserving an order clears recovery contact data immediately. The API sweeper deletes expired carts and their deliveries and removes behavior older than 7 days, even when Redis is not configured. Purge continues while the API is running; after downtime it catches up on the next sweep. Existing order data follows the existing retention policy.
- Recommendation personalization has separate, unchecked consent. Without it only the current product/cart and aggregate paid-order co-occurrence affect ranking. With it a random session is HMAC-hashed per tenant; only handles and VIEW/CART events are stored (maximum 300 per session). No email, phone, IP or contact matching is used. Withdrawal deletes that session's behavior; previews never record it.

## Delivery reliability

`RecoveryDelivery` is a durable outbox with a unique cart/revision/step/channel key. The reconciliation sweep enqueues delayed BullMQ jobs from pending rows every 30 seconds; queue data carries only tenant/delivery IDs. Multiple API instances can run workers: a PostgreSQL claim and cart-row lock enforce concurrency and at most 3 delivered/prepared/uncertain messages per channel per cart across all revisions.

States: PENDING → SENDING → SENT / PREVIEW / FAILED / UNCERTAIN; obsolete or stopped rows become CANCELLED. Definite provider throttling retries with exponential backoff, up to 5 attempts. Provider rejection becomes FAILED. Network timeouts, ambiguous server errors or a crash after claiming become UNCERTAIN and are not automatically resent. SES/Meta do not provide a universal idempotency guarantee; claiming exactly-once delivery across a crash would be incorrect. An unsubscribe cannot retract an already in-flight provider request. Reconcile uncertain sends in the provider's delivery logs before any manual follow-up.

The console shows saved selections, reservations attributed to recovery, and delivery counts for retained carts. These are operational counts, not a measured conversion uplift or paid-revenue attribution. Redis failure stops asynchronous sending without losing pending database rows; ranking has a database fallback. Redis eviction must stay disabled. Qdrant failure falls back to database affinity/co-purchases.

Email copy lists the selected items at current prices. Low-stock text appears only for tracked stock of at most 5 units; paid-order proof counts actual tenant orders containing the selected products over 30 days. Expiry refers to the actual recovery-link lifetime. There are no invented promotions, customer quotes, stock reservations or delivery claims. WhatsApp content is the merchant's approved template.

## Recommendations and performance

- Ranking uses tenant paid/fulfilled/shipped/completed orders over 90 days, category affinity from the selection/consented history, and genuine same-line upgrades or bundles containing a selected product.
- Qdrant adds cosine similarity over deterministic 128-dimensional catalog feature vectors (category/brand/product features); these are not LLM semantic embeddings. Its tenant catalog is indexed through a separate BullMQ worker in pages of 200, scheduled at most once per 15 minutes when that tenant requests an uncached ranking. A first request can fall back until the index is ready. Current availability is always checked in PostgreSQL, including deleted/unpublished vector matches.
- Redis caches ranked handles and reasons for 60 seconds, scoped by tenant and context. Response products always rehydrate current variants, stock, visibility and prices; checkout still performs authoritative amount/stock validation. Product/cart show up to 4 suggestions; checkout shows at most 1 optional offer, never preselected. Checkout reservations disable additions.
- Serving returns `Server-Timing: recommendations;dur=...`, forwarded by the same-origin proxy. Measure warm end-to-end latency with `node scripts/benchmark-recommendations.mjs STORE_ORIGIN PRODUCT_HANDLE`. It reports p50/p95 after 5 warmups and exits nonzero at p95 >= 50 ms. This is a target, not a verified guarantee; network, host resolution, database and rate-limit latency are included. Run on staging with realistic catalog/order volume and multiple tenants before release.

## Verification

Build all three apps. Unit coverage tests tenant-bound/tamper-proof capabilities, stopped/expired/revised carts, lost claims, per-channel cap, ambiguous delivery vs retry, current-price hydration, preview transport and escaped email content. `npm run test:docker` applies the migration to isolated `vendedoria_test` and includes `conversion-isolation.e2e-spec.ts` (cross-tenant restore/revoke/activity, forbidden client tenant input, visibility, live price/stock changes and contact deletion).

Staging acceptance: enable a tenant with 1/2/3-minute delays; opt in for one channel; keep interacting and confirm postponement; close the page and observe one reminder; restore on a second device; change stock/price; opt out; reserve/pay an order; interrupt/restart the API/Redis; confirm uncertain requests are not duplicated; disable recovery or unpublish the store. Repeat buyer widgets at 360, 768 and 1440 CSS pixels in all three templates. Verify real SES deliverability and Meta template delivery without logging PII or capability links. No live messages or infrastructure activation are performed by unit tests.
