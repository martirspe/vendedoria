# WhatsApp customer onboarding

VendedorIA connects each business's own WhatsApp Business Account (WABA) and phone in two modes: Meta Embedded Signup v4 or a customer-owned Meta app with Cloud API credentials. Only OWNER/ADMIN can configure or disconnect either mode. Both are available from Integrations and Channels. Exactly one connection is active per business; changing modes requires disconnecting first. Existing connections remain usable.

## Customer-owned app setup

This mode is independent of VendedorIA's Embedded Signup approval/configuration. It is intended for businesses that already manage their own Meta app, WABA, registered Cloud API phone and authorized token; it is not a workaround for Meta's provider requirements. Meta policy, account eligibility, messaging windows and approved-template rules apply to both modes.

1. Server prerequisites: HTTPS `PUBLIC_API_BASE_URL`, a valid `CHANNEL_CREDENTIALS_KEY` and `META_GRAPH_VERSION=v26.0`. Platform `META_APP_ID`, `META_APP_SECRET`, `META_VERIFY_TOKEN` and `META_WHATSAPP_CONFIG_ID` are not used for customer-owned app webhooks.
2. In Integrations choose **Credenciales propias**. Provide the business's App ID, 32-character app secret, access token, WABA ID and Phone Number ID. Prefer a dedicated system-user token with `whatsapp_business_management` and `whatsapp_business_messaging` and access only to the required assets. VendedorIA verifies token app/scopes/expiry and queries the WABA's phones; inactive/unregistered numbers are rejected. Configure registration in Meta first; this mode does not initiate coexistence or migrate numbers.
3. Credentials are encrypted and a pending connection is reserved. Copy its callback URL and generated verification token into the business app's WhatsApp webhook settings in Meta. Subscribe the `messages` field. This replaces that app's callback, so use a dedicated app if the current callback serves another integration. VendedorIA does not automatically overwrite app settings.
4. Choose **Verificar y activar**. Activation requires successful challenge verification plus an active exact matching app callback and `messages` subscription from Meta. VendedorIA subscribes that app to the WABA and confirms the subscription before exposing encrypted send credentials.
5. Send a real inbound message from another number and check its arrival and response in Messages. Tests mock Meta; successful builds/tests do not establish actual Meta delivery or account approval.
6. The callback is scoped to the connection. Every POST validates HMAC over raw bytes with the customer's encrypted app secret, then matches WABA, phone, channel and tenant. Shared platform callbacks cannot ingest customer-app connections. Pending/disconnected deliveries are ignored. Outgoing requests use that customer's app-secret proof.
7. Owner/admin can recover the connection-specific verification token through the authenticated no-store setup endpoint. App secrets/access tokens are never returned. Disconnect removes only the managed WABA app subscription, clears encrypted credentials and disables the callback locally; it does not deregister/delete the number or WABA. Cancelling an unactivated setup does not remove pre-existing app subscriptions. Explicit token revocation permits local disconnect; transient upstream failures keep the existing connection for retry.

API: `POST /channels/whatsapp/manual/connect` (also `/channels/whatsapp/connect` with the same validated DTO); `GET /channels/whatsapp/manual/:channelId/setup`; `POST /channels/whatsapp/manual/:channelId/activate`; existing diagnostics/disconnect routes select the correct mode. The public callback is `/webhooks/meta/whatsapp/manual/:channelId` (GET challenge, POST signed events). No additional database migration is needed for manual mode; connection metadata uses the existing Channel JSON column.

## Activate in Meta and production

The following steps enable **Conectar con Meta**. They are separate from customer-owned app setup above.

1. Complete the Tech Provider/Access Verification flow applicable to the app, Business Verification and App Review. Enable Advanced Access to `whatsapp_business_management` and `whatsapp_business_messaging` for external businesses. A verified company alone does not complete these app requirements.
2. In Facebook Login for Business / Embedded Signup Builder create the WhatsApp Embedded Signup **v4** configuration for customer-scoped business tokens. Enable the intended Cloud API onboarding flow and coexistence only if the app/account is eligible. Record its configuration ID. Do not use a generic Facebook Login configuration or a shared platform system-user token for customer authorization.
3. Configure the console's HTTPS domain in App Domains, Allowed Domains for the JavaScript SDK and the redirect settings required by Meta. Publish the app. Keep graph/SDK version aligned with the app's supported version (`v26.0` default; configurable).
4. Configure `https://<console-host>/api/v1/webhooks/meta/whatsapp` in the platform Meta app and subscribe to `messages`. Enter the platform's `META_VERIFY_TOKEN` there once. Customer businesses never receive this token or `META_APP_SECRET`. Production POST events require the app-secret HMAC signature over raw bytes.
5. Configure server environment: `META_APP_ID`, `META_WHATSAPP_CONFIG_ID`, `META_GRAPH_VERSION`, `META_APP_SECRET`, `META_VERIFY_TOKEN`, `CHANNEL_CREDENTIALS_KEY` and HTTPS `PUBLIC_API_BASE_URL`. Generate CHANNEL_CREDENTIALS_KEY as 32 cryptographically random bytes encoded as 64 hex characters. Store securely and back it up; changing it without re-encryption makes customer credentials unreadable. Leave CONFIG_ID unset until ready: the existing installation starts normally and the console explains availability.
6. Deploy the additive `20261009010000_whatsapp_embedded_signup` migration, API and console, and rebuild nginx so the console CSP permits Meta's SDK, Graph API and login frame origins. The store CSP remains separate.
7. Test an external business (not just an app administrator): new number + six-digit PIN, existing Cloud API number, eligible coexistence, cancellation/retry, revoked authorization, reconnect and disconnect. Receive a real inbound message from another number and confirm a reply in the tenant's inbox. Confirm another business cannot claim the WABA/number. Production billing and payment-method requirements for that WABA still belong to Meta/its authorized provider; this flow does not share a VendedorIA credit line.

## Connection lifecycle

- Server issues a ten-minute signup session bound to authenticated tenant/user and a random hashed state. The SDK and session are prepared before the user's click to preserve popup activation.
- OAuth code is exchanged immediately on the server without waiting for the popup's separate session-info event. Atomic session claims reject replay. The access token is AES-256-GCM encrypted; no access token or PIN is returned to the browser.
- Server verifies token validity, app ID, messaging/management permissions and granted WABA targets through `/debug_token`, then queries those WABAs for phone numbers. The user selects from this verified list. Every activation revalidates ownership. Popup IDs are never ownership evidence.
- Tenant, WABA and phone claims are serialized with PostgreSQL transaction advisory locks across replicas. An account cannot span different VendedorIA businesses. One active WhatsApp connection per business is supported. Disconnect before switching numbers.
- Unregistered ordinary Cloud API numbers require the customer's six-digit two-step PIN; `/register` is never called for coexistence. The backend subscribes the app to the WABA and confirms the subscription plus Cloud API `CONNECTED` status before exposing send credentials and marking the channel connected.
- Diagnosis checks current authorization, registration and subscription. Transient Meta failures preserve the previous state; revoked permissions degrade the connection and prompt reconnection. A diagnostic cannot resurrect a disconnected channel. Inbound deliveries to pending/disconnected channels are ignored.
- Disconnect unsubscribes this app from the customer's WABA for Embedded Signup connections and clears local send credentials and signup credentials. It does not delete the customer's WABA or deregister their phone. Transient Meta failures preserve the local connection for a retry. If Meta explicitly reports an expired/revoked token, disconnect clears the local association and ignores future deliveries; the business can also remove the app permissions in Meta. Legacy connections are disconnected locally, since their original app subscription is not managed by this onboarding flow.
- Failed/abandoned activations expose no send token. A reservation older than two minutes can be diagnosed and retried. Expired session credentials are removed on the next attempt in the same business; credentials in failed/cancelled/completed sessions are cleared immediately.
- Legacy plaintext credentials remain readable only for compatibility; successful reconnection replaces them with encrypted customer credentials. No legacy secret is returned through channel listings.
